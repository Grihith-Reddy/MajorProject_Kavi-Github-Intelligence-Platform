How KAVI works, pin to pin

Every box below is a real file, table, service or setting. Follow the arrows to see where data goes: from your browser, through the API on Render, into the Neon database, out to GitHub and Gemini, and back.

Live: kavi-memory.vercel.app → kavi-api-5af0.onrender.com (Singapore) → Neon (Singapore)
The diagrams are drawn by Mermaid, loaded from a CDN. You are offline, so you see each diagram's source text instead.

Website (Vercel)

Only frontend/ is built and published. Never sleeps. Security headers come from frontend/vercel.json.

API (Render)

One Python process: the FastAPI app plus a background thread that runs sync jobs. Sleeps after 15 idle minutes; UptimeRobot pings /health/live to keep it awake.

Database (Neon)

PostgreSQL with full-text search columns. Embeddings are stored as JSON and compared in Python, so no pgvector is needed. Pauses after 5 idle minutes and wakes in about a second.

Identity

Firebase proves who you are. A separate GitHub App proves which repositories you may read. KAVI's own tokens (Guardian, MCP) are for machines.

3 · Sign-in and GitHub connect

Two separate identities. Firebase signs you in to KAVI. Then a GitHub App authorisation (with PKCE) gives KAVI a read-only GitHub token, which is encrypted before it is stored.

sequenceDiagram
  autonumber
  actor U as You
  participant S as SPA
  participant F as Firebase
  participant A as API
  participant D as Neon
  participant G as GitHub
  U->>S: Open /login · Google or email
  S->>F: signInWithPopup / signInWithEmailAndPassword
  F-->>S: ID token (JWT, refreshed automatically)
  S->>A: GET /api/github/status · Bearer ID token
  A->>F: verify_id_token(check_revoked)
  A->>D: upsert users row
  A-->>S: connected: false → show /connect-github
  U->>S: Continue with GitHub
  S->>A: GET /api/github/connect-url
  A->>D: github_oauth_states · state + PKCE verifier (Fernet-encrypted, 10 min)
  A-->>S: github.com/login/oauth/authorize?client_id, state, code_challenge
  S->>G: redirect · you authorise "Kavi Memory"
  G->>A: GET /api/github/callback?code&state
  A->>D: DELETE state RETURNING verifier (single use)
  A->>G: exchange code + verifier → user access token
  A->>G: GET /user
  A->>D: github_accounts · token Fernet-encrypted
  A-->>S: redirect → /repositories
KAVI refuses expiring GitHub tokens, so "Expire user authorization tokens" must stay off in the GitHub App. Repositories appear only where the app is installed.

4 · Sync pipeline (turning PRs into memory)

A sync is a queued job. The worker thread inside the API claims it, reads only PRs updated since the last sync, summarises each one with Gemini, and writes everything KAVI later searches.

flowchart TB
  CL(["Sync button"]) --> EP["POST /api/ingestion/repositories/sync
repo_full_name · full_resync"]
  EP --> Q[("sync_jobs · queued")]
  Q --> CLM["Worker claims job
FOR UPDATE SKIP LOCKED · attempt + 1"]
  CLM --> TOK["Decrypt the user's GitHub token"]
  TOK --> LST["list_pull_requests_updated_since
cursor = repositories.last_pr_updated_at"]
  LST --> LOOP{{"For each new or changed PR"}}
  LOOP --> FETCH["Fetch details, files and patches,
commits, reviews, review and issue comments"]
  FETCH --> PAY["_build_pr_payload
compact and size-capped"]
  PAY --> AI["Gemini summary
intent · decisions · risks · tags
falls back across models on quota"]
  AI --> UPS["Upsert pull_requests, commits,
knowledge_entries, file_mappings,
pr_participants"]
  UPS --> PRM["extract_promises
heuristics + AI confirmation → pr_promises"]
  PRM --> PROG["update_sync_job_progress
phase · processed/total · current PR"]
  PROG --> LOOP
  LOOP -->|"done"| ENR["run_post_sync_enrichment
backfill embeddings · resolve kept promises"]
  ENR --> OK[("sync_jobs · succeeded
cursor advanced")]
  CLM -. "on error" .-> RETRY["retry up to 4 attempts · 30 s apart
stale after 15 min → recycled"]
  UI(["Progress capsule in the UI"]) -. "polls GET /api/ingestion/jobs/{id}" .-> PROG

File mappings

Line ranges come from each patch's hunk headers, so a PR is linked to the exact lines it touched. Why-Lens and Guardian both use them.

Incremental

Only PRs updated after last_pr_updated_at are read; unchanged ones are skipped by a payload hash. "Full resync" ignores the cursor.

Fallback worker

python -m app.workers.ingestion_worker --once runs the same claim loop. It is also available as a manual GitHub Actions workflow.

Chat streams. The API runs Gemini with function calling over eight KAVI tools, and sends each step and token to the browser as Server-Sent Events while it works.

6 · Hybrid memory search

Three rankings of the same knowledge entries, merged by Reciprocal Rank Fusion, so an entry that ranks well on meaning and on exact words rises to the top.

flowchart LR
  Q(["Question"]) --> SEM["Semantic
Gemini embedding of the question
cosine vs stored vectors
local embedder if no key"]
  Q --> FTS["Full-text
PostgreSQL tsvector + ts_rank"]
  Q --> KW["Keyword
ILIKE on summary, intent,
PR title and body, file paths"]
  SEM --> RRF["reciprocal_rank_fusion
score = Σ 1 / (60 + rank)"]
  FTS --> RRF
  KW --> RRF
  RRF --> TOP["Top entries + their PRs and files
→ agent context and citation chips"]

8 · Guardian

A GitHub Action in your repository asks KAVI to review each new PR against past decisions and open promises, then posts the verdict as a comment. KAVI itself never writes to GitHub.

sequenceDiagram
  autonumber
  actor Dev as Developer
  participant GA as Guardian Action (kavi-guardian.yml)
  participant A as API /guardian
  participant D as Neon
  participant L as Gemini
  Dev->>GA: opens or updates a PR
  GA->>A: POST /review · Bearer kavi_gd_ token · {pr, files + patches}
  A->>D: token hash → owner still has access? (bound to one repo)
  A->>D: gather_history (past PRs on the same files) · matching_promises
  A->>D: predict_change_impact · suggest_reviewers
  A->>L: judge the change against that history
  L-->>A: verdict + findings (history-only fallback if AI is unavailable)
  A->>D: guardian_reviews row (impact, reviewers)
  A-->>GA: comment_markdown
  GA->>Dev: posts or updates the PR comment
  Note over GA,A: On merge the Action calls POST /guardian/sync → incremental sync job

9 · Insights

Promises

  • Found during sync: "follow-up", "temporary", TODO
  • resolve_promises asks Gemini whether a later PR kept one
  • Stats: open, kept, oldest open, median days to keep

Knowledge map

  • Files grouped into modules (two folders deep)
  • Each person's share of a module's PRs → bus factor
  • At-risk when the main experts have gone quiet
  • Co-change edges from PRs that touch two modules

Quality harness

  • Samples entries, Gemini writes questions
  • Runs full-text, semantic and hybrid search
  • Recall@k, MRR and a faithfulness judge → eval_runs

Repository health

GET /api/insights/health feeds the chips on the Repositories page: open promises, at-risk modules, sync freshness.

13 · Security model

LayerWhat protects it
Who you areFirebase ID token on every call, verified with revocation checks and a small clock-skew allowance
What you can readassert_repo_access on every repo route; IDs must be UUIDs; other routes are scoped to your own user id
GitHubGitHub App with read-only Contents, Pull requests, Issues; PKCE + signed single-use state; token encrypted at rest
Machine tokensGuardian and MCP tokens shown once, stored hashed, revocable, Guardian tokens bound to one repo
TransportHTTPS everywhere; HSTS; database connections require TLS
BrowserCORS limited to the website's origin; CSP and frame denial; same-site-only login redirects; repo ids validated before use
AbusePer-user rate limits, 256 KB body limit, proxy headers trusted so limits see real client IPs
SQLEvery value is a bound parameter; migrations contain no grants or privileged functions
ErrorsUnexpected failures return a generic message and a request id; details stay in the server log
